# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm install` — install dependencies (Electron, electron-vite, Vite, React and Tailwind; all are dev dependencies because the renderer is bundled).
- `npm run dev` — run the app with Vite hot reload for the renderer (`electron-vite dev`).
- `npm run build` — build to `out/main`, `out/preload` and `out/renderer`.
- `npm start` — build, then launch the production build (`electron-vite preview`). `package.json` `main` points at the built `out/main/main.js`, so plain `electron .` only works after a build.
- `npm run check:keys` — verify the accounts and keys in `.env` with one read-only call each (Groq, Telegram, Supabase, Ollama, Claude CLI, git hygiene); never prints a secret. `npm run check:keys -- --find-telegram-chat` lists the chat IDs that messaged your bot.
- `npm run db:migrate` — apply `supabase/migrations/*.sql` to your Supabase project through the management API (needs `SUPABASE_ACCESS_TOKEN` in `.env`; use `-- --dry-run` first). Records applied migrations, refuses to run over a project that already has tables or to apply out of order. Add new migrations as new files; never edit an applied one.
- `npm run check:db` — after applying the migrations to your Supabase project, check that all 16 core tables exist (read-only; uses `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`).
- `npm test` — unit tests (`node --test` over `.claude/**/*.test.js`, `src/**/*.test.js` and `scripts/**/*.test.js`; the globs are explicit because Node's default discovery skips dot-directories). Single file: `node --test .claude/evals/lib.test.js`.
- `npm run eval` — run all eval suites in `.claude/evals/suites/`. One suite: `node .claude/evals/run.js policy-check`. Add `--verbose` to list every case.
- `npm run gate:1` — the Phase 1 gate scenario (`scripts/gate1.js`): a fake agent proposes a spend, the card reaches Telegram and the dashboard, one tap approves it, the purchase happens once, and `audit_log` has every step. Real app and database, fake Telegram, model and purchase tool; also graded by the `phase1-gate` eval.
- `npm run gate:2` — the Phase 2 gate scenario (`scripts/gate2.js`): a lead goes to a reviewed proposal on a founder card, a routine ticket is answered, a refund ticket becomes a spend card, the phone's `/brief` matches the window, one tap approves or rejects and an approved email is sent exactly once. Real app and database, fake Telegram, Tavily, model and mail transport; also graded by the `phase2-gate` eval.
- `npm run gate:3` — the Phase 3 gate scenario (`scripts/gate3.js`): two pods are asked for on cards and opened on approval, an agent opens exactly one pull request in its own pod's repository (a production deploy becomes a card), an invoice draft is produced in the other pod (a payment request becomes a card), and the two pods never see each other's files, notes or repository. Real app, database, git and pods service; fake GitHub, model and remote locations (`createApp`'s `gitRemoteUrl` test hook); also graded by the `phase3-gate` eval.
- `npm run pod -- propose --name "Acme site" --template agency_client [--client-id … --service … --priority P1 --deadline 2026-12-31 --note …]` / `list` — ask for a project space (a founder card; nothing is made until you approve it) or list the pods (`scripts/pod.js`). Needs `PODS_ROOT` in `.env`.
- `npm run pod -- priority <pod id> P1|P2|P3` / `queue` — change a project's priority (audited; shared specialists serve the highest priority first), or list the work waiting for shared specialists in the order it will be served (`scripts/pod.js`).
- `npm run engineer -- --pod <pod id> --title "Add a contact page" [--description …]` — give the Engineering team one task inside one pod (`scripts/engineer.js`; find the pod id with `npm run pod -- list`). It makes the change on a branch, sends it to the pod's GitHub repository (when it has one) and opens a pull request; a merge or a production deploy is a founder card. Needs `PODS_ROOT` (and `GITHUB_TOKEN`/`GITHUB_REPOS` for pull requests).
- Telegram `/finance [project |] <what to do>` and `/engineer <project> | <what to do>`, and the Teams page's two forms (`teams.startFinance`, `teams.startEngineer`), start the Finance and Engineering teams the way `/lead` and `/ticket` start the others (background, two at a time, result as a second message, anything it needs as a card). A project is named in words and found among the open pods. Graded by `team-tasks`.
- `npm run finance -- --title "Invoice Acme Studio" [--description …] [--pod <pod id>]` — give the Finance, Legal and Ops team one task (`scripts/finance.js`): a draft invoice with the GST worked out in code, an expense record, a contract reading or a data-privacy check. With `--pod` it is that project's work. Nothing is paid, signed, sent or issued: a payout, a signature or a legal document is a founder card. Needs a model provider and Supabase (and `PODS_ROOT` with `--pod`).
- `npm run lead -- --company "Acme Ltd" [--website https://… --email … --price …]` — give the Marketing and Sales team one lead (`scripts/lead.js`), with the real accounts in `.env` (Supabase, a model provider, `TAVILY_API_KEY`). It researches, saves the lead and puts a proposal email on a founder card; nothing is sent to the company.
- `npm run ticket -- add --email … --subject … --message …` / `work [--id …]` / `list` — add a support ticket, give it (or the oldest open one) to the Support team, or list the latest (`scripts/ticket.js`). Needs the `tickets` table (`npm run db:migrate`). Nothing is sent to the customer.
- `npm run eval:strict` — same, but suites whose code isn't written yet count as failures. Use this at phase gates.

There is no linter configured yet. `out/` (build output) and `dist/` (reserved for packaging) are gitignored.

## Evals

The plan (`.claude/PLAN.md`) is eval-first: golden datasets in `.claude/evals/datasets/` are written before the code they grade. A suite (`.claude/evals/suites/*.js`) exports `{ name, description, threshold, cases(), run(case) }`. If the module under test doesn't exist, the case is reported as **pending**, not failed (`loadSubject` in `.claude/evals/lib.js`). The input/output contracts for `src/runtime/policy.js`, `src/runtime/cards.js` and `src/runtime/providers/claude-code.js` are in the header comments of `.claude/evals/suites/policy-check.js`, `decision-cards.js` and `claude-code-provider.js`. When adding a feature, add its eval cases first.

`.claude/EVALS.md` is the registry of every eval (suites, case counts, status, planned evals). Update it in the same change as any eval you add, remove or edit; the `evals-doc-in-sync` check in the `invariants` suite fails if a suite is missing there or its `**Cases:**` count is stale.

## Architecture

Electron app built with `electron-vite` (Vite 8): main and preload are plain CommonJS JavaScript, the renderer is React 19 (JSX). The standard three-process split, with sources at the paths below and `electron.vite.config.mjs` mapping them to `out/`:

- `src/main.js` → `out/main/main.js` — main process. Creates a single 900×600 `BrowserWindow`, loads the Vite dev server URL (`ELECTRON_RENDERER_URL`, set by `npm run dev`) or the built `out/renderer/index.html`. Quits on window close except on macOS. Before the window loads it creates the runtime (`createApp` from `src/runtime/`) and the IPC bridge (`src/ipc.js`); it then calls `runtime.start()` (records `runtime.started`, or blocks the runtime if the database is not ready) and records `runtime.stopped` on quit. It loads `.env` from the app folder; settings already in the environment win.
- `src/preload.js` → `out/preload/preload.js` — the only bridge between main and renderer. Exposes `window.versions` (Node/Chrome/Electron versions) and `window.api` (`runtime.status`, `decisions.list`, `decisions.resolve`, `goals.list`, `teams.list`, `brief.get`, `agents.list`, `agents.events`, `agents.pause`, `agents.message`, `agents.reassign`, `files.*`, `onEvent`) and nothing else. Each function sends one fixed message on the `runtime:invoke` channel (events arrive on `runtime:event`); `ipcRenderer` itself is never exposed, and two invariants enforce that. To add a capability: register a command in `src/runtime/commands.js`, add one function to `window.api`, and extend the `runtime-core` eval first. Main finds it at `../preload/preload.js` relative to the built main file.
- `src/renderer/` → `out/renderer/` — sandboxed React UI. `index.html` loads `main.jsx`, which mounts `App.jsx` and imports `styles.css`. `App.jsx` shows the runtime status and mounts `GoalsPanel.jsx` (the founder's goals and where each stands), `ApprovalQueue.jsx` (the waiting decisions) and `BriefPanel.jsx` (today's brief: the lines `brief.get` gives, nothing written in the renderer), `TeamsPanel.jsx` (each team's agents, open and blocked tasks; what it shows is decided by `teams.mjs`, graded by the `teams-view` eval), all kept live from runtime events instead of polling (the Teams page also reloads on window focus and from a Refresh button, because work done by another process announces nothing); what the queue shows and how an answer is built lives in `queue.mjs`, and what a goal shows lives in `goals.mjs` (including the Download button: one file as itself, several as a `.zip` built by `zip.mjs`), graded by the `approval-queue`, `goals-view` and `zip-file` evals. Styling is Tailwind CSS 4: `styles.css` is just `@import 'tailwindcss'`, components use utility classes, and the `@tailwindcss/vite` plugin in `electron.vite.config.mjs` generates the CSS. There is no `tailwind.config.js` or PostCSS config (v4 is CSS-first): add design tokens with `@theme { … }` in `styles.css`.

Reserved directories, empty until their plan steps (see `.claude/PLAN.md`): `src/shared/` (so far only `supabase-url.js`). `config/mcp/shared.yaml` is the tool allow-list, and `.claude/skills/shared/` holds the base prompts for every agent: `company-charter` (draft), `plain-language-approval`, `escalation-rules` and `handoff-notes` (the last three are graded by the `shared-skills` eval). Environment variable names are in `.env.example`; real values go in the gitignored `.env`.

### Runtime

`src/runtime/` is the agent engine and **must never import `electron`** (an invariant enforces it), so it can later run headless on a server. `createApp({ env })` in `index.js` wires `config.js` (validates settings) → `store/rest.js` (Supabase REST API with the service key) → `audit.js` (the `audit_log` writer, redacts secrets) → `runtime.js` (the command bus) → `commands.js` (the registered commands). The bus enforces, and the `runtime-core` eval tests: unknown commands and bad arguments are refused; **the audit entry is written before a handler runs, and if it cannot be written the handler does not run**; errors returned to the UI are generic. Commands are audited by default; use `audit: 'never'` only for health checks. `policy.js` is the policy check: `checkAction({ tool, access, args?, note? })` returns `{ allowed, category }`, is plain code (no model), and denies any tool not listed in its `RULES` table, so adding a tool means adding a line there in review. Free text never changes the answer, and an invariant keeps `policy.js` the only place that builds an `allowed: true` answer. `cards.js` is the plain-language card layer: `checkCard(card)` (plain code) rejects jargon, code, a missing field, a bad risk level, a cost without both ₹ and $, and a time without IST; `produceCard({ request, write, maxAttempts })` runs a writer function until a card passes or the limit is reached, and a card that never passes comes back `flagged` with no `card` property so it cannot be sent; `writerInstructions()` is the writer's rule text, built from the checker's own lists. The writer is passed in, so `cards.js` never calls a model. `decisions.js` is the decisions service (`createApp` builds it and exposes it as `app.decisions`): `create` (category from the policy check, card through the checker), `resolve` (one atomic "update where status is still ... " write, so the phone and the dashboard answering at once take effect once; only the founder's channels `dashboard` and `telegram`), `cancel`, `get` and `remindDue` (counts reminders, never touches a status). It audits before it writes, refuses while the runtime is blocked, and is for trusted code only: never hand `resolve` to an agent's tools. An invariant keeps it the only code that writes a decision's status. `policy-tools.js` lets the founder add tools to the policy check from Telegram (the bot is step 1.8): built-in rules in `policy.js` always win, the founder's additions live in the `policy_tools` table (service key only) and are merged in through `createPolicy`; an always-ask addition is active at once, a routine one (which loosens the rules) needs a confirm, removal is immediate. `tools/` is the tool loader (`createToolLoader`, built in `createApp`): a tool only loads if it has a policy rule (built-in or the founder's active one), the rule is checked again on every call, and a tool's result is reduced to plain text plus at most one clean file `{ name, content }` (`tools/files.js`); `tools/filesystem.js` makes the read-only Filesystem tools (`filesystem.read_file`, `filesystem.list_directory`) for ONE folder (`FILESYSTEM_ROOT`, or the app's own folder passed by `main.js`; with neither there are none): nothing outside it, no links that leave it, no secrets (`.env*`, `.git`, `node_modules`, keys), text only. `tools/config.js` reads `config/mcp/shared.yaml` (plus `<team>.yaml`): an allow-list with a read/write tag check that fails closed, and `createApp` loads only the tools it lists; `tools/fetch.js` (`fetch.get`: public https only, never a private or metadata address, checked again at connect time), `tools/github.js` (only the repositories in `GITHUB_REPOS`; merging always asks) and `tools/supabase.js` (`supabase.select` on four non-sensitive tables, select only) complete the tool set. `tools/builtin.js` holds the built-in `docs.create_draft`, whose text and file reach Telegram and the window's Download button. `createApp` builds it as `app.policyTools` and loads the rules at start (if the table is missing the runtime runs on the built-in rules and emits `policy.degraded`); the decisions service uses its live `policy`. Only `policy-tools.js` may touch that table (an invariant), and it, like `resolve`, is never handed to an agent. If settings are missing or the audit log cannot be written, the runtime blocks itself: it refuses actions with the reason and still answers `runtime.status`. For development without your real tables, `node scripts/fake-supabase.js` starts a local stand-in for Supabase's REST API (a real Postgres with the migrations) and prints the two settings to run `npm run dev` against it; `src/runtime/runtime.integration.test.js` uses the same stand-in.

### Agents

`src/runtime/agents/` is the team framework (step 2.1; `createApp` builds the factory as `app.agents`, with limits of 10 steps and 60,000 tokens per worker run, sized for the real skills; the teams are Marketing and Sales in 2.3 and Support in 2.4). `createAgentFactory({ router, store, audit, policy, catalogue, hasRule, configDir, skillsDir, limits })` in `index.js` builds a team of one lead and its workers from `shared` plus that team's tools (`config/mcp/<team>.yaml`, through the tool loader, so a tool needs a policy rule) and skills (`.claude/skills/<team>/`); it refuses to build without the `company-charter` skill. `agent.js` is one agent's loop: one JSON action per model call, tools only from its team, under step and token caps, a tool run audited first; **the real policy check decides what is crucial: an action that needs the founder is never run, the agent stops and hands the request back**. `lead.js` plans a task into subtasks and reviews each worker output (a review is an accept only when it says `accept: true` exactly). `team.js` runs a task through `tasks` rows: queued, in_progress, in_review, done, and done only after the lead accepted every output; a rejected output goes back once with the lead's feedback, then the task is blocked. Every change is audited before it is made. Graded by the `skills-loader`, `agent-loop` and `team-framework` evals. `team.js` also tells the app when a task or an agent changes (`onChange`, a hint that can never stop a task; `createApp` turns it into the `tasks.changed` runtime event), and `teams/overview.js` answers the window's `teams.list` command with each team's agents, counts and open and blocked tasks, plain short fields only (graded by `teams-overview`).

### Outbound messages

`src/runtime/outbound/` is the gate every message to a client goes through (step 2.2); `createApp` builds it as `app.outbound` and takes an optional `mailSend` transport (none is connected yet: the founder chose Gmail drafts only for step 2.3, so with none, nothing can be sent). `service.js`: `submit` checks the message in code, refuses a second email from the same team to an address that already has one waiting for the founder or approved and not yet sent (status `duplicate`, with the first one's message id), saves it to `outbound_messages` (audited first), has it reviewed (`review.js`: code checks, then a model that can only make it stricter and fails closed), and then marks it ready or files a decision card (category legal or public, the email text under "Show details", tool name `outbound.approve_send`); `send` is the only way out and sends only a message that is `ready`, the STORED text, once. The founder approves every message unless `OUTBOUND_FOUNDER_APPROVAL_UNTIL` (the last day of the first weeks, for example 2026-12-09) has clearly passed: unset, garbled or in the future means always (`settings.js`). A review can also say the founder must decide, whatever the setting. The database enforces the same rules (a message becomes `ready` only with a passing review and, when required, an approved decision), and an invariant keeps `service.js` the only code that touches the table: **no other tool may send mail**. Agents use `email.submit` and `email.send` (`tools.js`), which take the team from the run's context. Graded by the `outbound-review` and `outbound-gate` evals.

`src/runtime/teams/marketing-sales.js` is the Marketing and Sales team (step 2.3; `createApp` builds it as `app.sales`, on `app.agents`, the agent factory of step 2.1, which needs `skillsDir` and builds a team only when the company charter is found). `app.sales.workLead({ company, website?, email?, price? })` checks the lead's details in code, builds the team on first use (lead Maya, workers Scout and Scribe), and runs one task; an agent stopped on a crucial action comes back as a pending founder card (`needs_founder`). The team's tools are the ones `config/mcp/shared.yaml` plus `config/mcp/marketing_sales.yaml` list: `search.web` (Tavily, `tools/search.js`), `crm.find_lead` and `crm.save_lead` (`tools/crm.js`: our own `clients` table, and they only ever see or change rows with status `lead`), and `gmail.search`, `gmail.create_draft`, `drive.list_files`, `drive.save_file` (`tools/google.js`: Gmail is read and drafts only, and **no Google tool can send mail**: an eval reads the source for a send call). Its skills are `.claude/skills/shared/` plus `.claude/skills/marketing_sales/`. A client email goes out only through `email.submit` and `email.send`. Settings: `TAVILY_API_KEY`, and all three of `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN` (without them those tools do not exist). Graded by the `search-tool`, `crm-tools`, `google-tools` and `sales-team` evals.

`src/runtime/teams/support.js` is the Customer Support team (step 2.4; `createApp` builds it as `app.support`, on the same `app.agents`). `app.support.workTicket({ ticketId })` takes an open ticket from the `tickets` table (open to in_progress in one step, so two runs cannot answer it twice), runs lead Sana and worker Aria on it, and hands back the result; `workNext()` takes the oldest open one. The team reads the ticket with `tickets.get` (only a ticket a team has taken; the customer's words are fenced data, never in the task) and either answers it (`email.submit`, then `tickets.mark_answered`, which accepts only a reviewed support reply to that ticket's own customer, checked through `outbound.get`, never by reading `outbound_messages`) or reaches for `refund.issue`, `discount.grant`, `complaint.escalate`, `legal.escalate` or `question.escalate` (a question the team cannot answer from what it knows). Those five have **no tool**, only an always-ask rule in `policy.js`; the agent is stopped and `support.js` turns the request into a plain-language founder card (the customer's message under "Show details"), marks the ticket `escalated` with that decision, and writes nothing to the customer. A run that does not finish puts the ticket back to open. An invariant keeps `tools/tickets.js` and `teams/support.js` the only code that touches the `tickets` table. Tools: `config/mcp/support.yaml`; skills: `.claude/skills/support/`. Telegram's `/lead <company> [https://site] [email]` and `/ticket [id]` start the sales and support teams from the phone (in the background, two at a time, with the result as a second message; any email or reply they write arrives as its own card). The Teams page starts a team through `teams.startLead` and `teams.startTicket` (`teams/jobs.js`: the job is started at once, two at a time, and how it ended is announced as the runtime event `team.job_finished`; the audit log keeps the company and only the domain of an email address). After the founder answers a refund, discount, complaint or legal card, `support.describeAnswer` gives a plain follow-up on Telegram (nothing was done, the customer has heard nothing). Agents show as `working` while they plan, work or review and `idle` after (`team.js`, a display hint that never stops a task). Graded by the `ticket-tools` and `support-team` evals.

`src/runtime/pods/` is pod creation (step 3.1; `createApp` builds it as `app.pods`, with `podTemplatesDir` and `podsRoot` passed by `main.js`; `PODS_ROOT` in `.env` wins; with neither, a pod can neither be asked for nor opened). `service.js`: `propose({ name, template, clientId?, service?, priority?, deadline?, note? })` files one founder card (action `pod.create`, an always-ask rule with no tool, category people or contracts) and writes nothing else; `open(decisionId)` applies an APPROVED card: the project row, a folder named from the project and the first part of the decision id (always directly inside the projects folder) with the template's files filled in, a git history with one commit (git run with no shell, hooks or machine settings), the pod row, one first memory note and the template's agents (not shared or removed ones). Every step is safe to run again and never overwrites a file; it is audited first, the founder's note never reaches the audit log, and on start the service opens any approved card that has no pod. The database refuses a pod on any decision but an approved `pod.create`, one decision opens one pod, and a pod's project, kind and decision cannot change (migration `20261126000000_pod_decision.sql`). `templates.js` reads `config/pods/<template>/template.yaml` (description, teams, files) and the files next to it; `npm run pod -- propose …` asks for a pod and `npm run pod -- list` lists them. Graded by `pod-creation` and two cases in `database-schema`.

**Pod isolation (step 3.2).** A task for a pod (`team.runTask({ podId })`, which needs an open pod) is saved with `tasks.pod_id`, and the agent loop puts the pod in every tool run's `context.podId`; the model never supplies it, and no tool takes a pod, repository, path outside its folder, table or client id as an argument. `tools/index.js` (the loader) refuses, in a run that has a pod, any tool without `podAccess: 'scoped'` (it reads the pod from its context) or `'neutral'` (it touches nothing of the company), and `describe({ inPod: true })` lists only those: a new tool is closed to pods until someone decides. The file tools read the pod's folder in a pod run and the company folder otherwise, and never the pods' folders (`podsRoot`); `supabase.select` returns only the pod's tasks, project and members; `tools/git.js` (`git.status`, `git.log`, `git.diff`: read only, the pod's own `.git` folder, never a link, with git told that folder is the whole world), `tools/memory.js` (`memory.recall`, `memory.remember`: one space per pod and one for the company; an odd pod id never falls back to the company) and `tools/pod.js` (`pod.get_client`: the run's own client). A team gets them only by listing them in `config/mcp/<team>.yaml` (none does yet). An invariant keeps `tools/memory.js` and `pods/service.js` the only code that touches the `memory` table. Graded by `pod-isolation`, one case in `database-schema` (every table with a `pod_id` column is covered) and the invariant.

**Engineering team (step 3.3).** `teams/engineering.js` (`createApp` builds it as `app.engineering`, on `app.agents`): `workTask({ podId, title, description? })` checks the details in code, builds the team on first use (lead Kavya, workers Dev and Tess; tools from `config/mcp/product_engineering.yaml`, skills from `.claude/skills/product_engineering/`) and runs one task inside ONE pod. Dev changes the project on a branch (`pod.write_file`, `git.create_branch`, `git.commit`, `git.push_branch`) and opens a pull request (`github.create_pull_request`); Tess reviews (`git.diff`, `git.log`). Writing tools: `tools/pod-files.js` (one file, inside the pod folder, links followed twice, never a secret name or `.git`); `tools/git.js` adds `git.create_branch`, `git.commit` and `git.push_branch` (branches named feature/, fix/, chore/, docs/ or test/ only: nothing can create, commit to or push the main line; a commit is refused when a secret file name or something that looks like a key is staged; a push goes to the repository tied to the pod, takes the token in the environment, and is never forced; a refusal the agent can act on comes back as a "Not done: …" result, because the loader never shows an error's own text). `tools/github.js` in a pod run works only on the pod's own repository (`podRepo`), never opens a pull request from the main line, and its merge tool is closed to pods. A pod is tied to a repository from the founder's list on its approved card (`projects.github_repo`, set once, migration `20261127000000_pod_repo.sql`). `tools/context7.js` (library documentation from `context7.com` only, `CONTEXT7_API_KEY` optional) and `tools/browser.js` (`browser.check_page`: public https pages only, the same check for every request the page makes, a stand-in driver in tests, Playwright only when it is installed). **There is no tool that merges or deploys**: a stopped agent's request becomes a plain card tied to the pod (`decisions.create({ …, podId })`) and the task is blocked; `describeAnswer` gives the phone's follow-up (nothing was done). Graded by `engineering-tools` and `engineering-team`.

**Finance, Legal and Ops team (step 3.4).** `teams/finance-legal-ops.js` (`createApp` builds it as `app.finance`, on `app.agents`): `workTask({ title, description?, podId? })` checks the details in code, builds the team on first use (lead Anika, workers Arjun and Leela; tools from `config/mcp/finance_legal_ops.yaml`, skills from `.claude/skills/finance_legal_ops/`: invoice-with-gst, expense-recording, contract-review, data-privacy-check) and runs one task, the company's or one pod's. Its one tool is `invoice.draft` (`tools/invoice.js`, `podAccess: 'neutral'`): the GST is worked out in code in whole paise, never by the model (CGST and SGST when the buyer is in the seller's state, IGST otherwise; a half rounds half up so the parts always add up), and the draft has no invoice number (the founder assigns it) and is never sent. **The team holds no payment credentials**: there is no Razorpay or Zoho tool (an invariant-style case in `finance-tools` reads the source for a credential), and `razorpay.create_payout`, `vendor.sign_agreement`, `docusign.send_for_signature`, `legal.issue_document` and `legal.escalate` have only always-ask rules in `policy.js`. A stopped agent's request becomes a plain card (tied to the pod when there is one) and the task is blocked; `describeAnswer` (chained after support's and engineering's in `createApp`, and ignoring a card that names a ticket) says nothing was done. Expenses are draft records written with `docs.create_draft`. Graded by `finance-tools` and `finance-team`.

**Priority and shared specialists (step 3.5).** `src/runtime/specialists.js` (`createApp` builds it as `app.specialists`, and the brief reads it): a pod asks a shared specialist (`agents.is_shared`, role `specialist`) for work with `request` (a queued `tasks` row of that pod assigned to the specialist; only an open pod, only a shared working specialist), and the specialist's caller takes the next one with `serveNext` (an atomic "update where status is still queued", so a task is handed out once even when two callers ask at once; a paused or removed specialist serves nothing). The order is the project's **current** priority (P1, P2, P3) and then the oldest request, so `pods.setPriority` re-orders what is waiting; nothing running is interrupted. The served task names its pod, so the run that works it belongs to that pod only (step 3.2). Everything is audited first, and nothing changes if the audit entry cannot be written or the runtime is blocked. `serveNext` is for trusted code and is never handed to an agent. Graded by `specialist-queue`.

**Project files panel (step 3.6).** `src/runtime/pods/files.js` (`createApp` builds it as `app.podFiles`, exposed to the window as the `files.*` commands and `window.api.files`): the founder reads a pod's file tree and git history, opens a file for editing (`beginEdit` locks it for agents, in memory, for 30 minutes, renewed by opening again), saves it (`save` writes the file and commits only that file as "Founder", releases the lock and emits `pod.file_changed`) or adds a new file (`upload`, never over an existing one). `pod.write_file` takes an `isLocked` function and refuses a locked file with a plain "Not done" result. Same path rules as `pod.write_file` (`checkTarget` in `tools/pod-files.js`): inside the pod folder only, no secrets, `.git` or links, text only. Audited first (path and size, never the words); nothing changes when the audit log is down, the runtime is blocked or git cannot record it. For trusted code only: never hand it to an agent. The panel is `FilesPanel.jsx` with its logic in `files.mjs`. Graded by `pod-files`.

**Agents panel and live feed (step 3.7).** `src/runtime/agents/events.js` (`app.agentEvents`) saves every step an agent takes to `agent_events` and announces it as the runtime event `agent.event` (saved first, then announced; it never throws and never stops an agent); the agent loop (`agent.js`) records a plain line before each tool runs (never the arguments or a tool's error text), `team.js` records when an agent starts working or goes idle. `src/runtime/agents/control.js` (`app.agentControl`, for trusted code only: never hand it to an agent) is the founder's side: `pause` sets the agent's status to `paused` and the loop asks `isPaused` before every step, so it stops at its next step (a team task is then blocked with a plain reason); `message` queues a note (in memory, up to 20) that the loop puts in the next prompt inside a random `FOUNDER-…` fence; `reassign` moves a waiting or blocked task to a working agent of the same team (a shared specialist's only to another shared specialist). Commands `agents.list`, `agents.events`, `agents.pause`, `agents.message`, `agents.reassign`; the audit log gets the length of a note, never its words. The panel is `AgentsPanel.jsx` with its logic in `agents.mjs`. Graded by `agents-panel`.

**Resuming a task after you approve its card (Option B).** The Engineering and Finance teams file their cards WITH the task (`decisions.task_id`). `src/runtime/teams/resume.js` (`app.taskResumer`, started and stopped with the runtime) listens for `decision.resolved`: an APPROVED card of those two teams (a deploy, a merge, a payout, a signature, an issued legal document; never a support ticket's card), whose task is still `blocked`, is audited (`task.resumed`) and then moves the SAME task back to `queued` in one atomic write, and the team's `resume` carries on in that row (`team.runTask({ resumeTaskId, resumeNote })`, no new row). Every worker is told that the approval is only the founder's answer, that nothing was merged, put live, paid or signed by it, and to say what is left for a person; there is still no tool that does any of those. If the continued work needs the founder again it files a NEW card for the same task and blocks it again. A card approved while the app was closed is picked up on start, once. One run at a time; a team that cannot start puts the task back to blocked; how it ended is the `team.job_finished` event. Graded by `task-resume`.

`src/runtime/brief.js` is the daily brief (step 2.6): `createBrief({ store, decisions, specialists }).get()` builds one headline and seven sections (Waiting for you, Revenue, Leads, Tickets, Deployments, Spend requests, Shared specialists: every shared specialist that more than one project is waiting for, who goes first and who waits, read through `specialists.conflicts()`), each a few plain lines, with the date and time in IST and "recent" meaning the last 24 hours. Revenue and Deployments say "Not tracked yet" because no payments or deployment tool are connected: no number is invented. It reads decisions only through `decisions.summary` (kinds, amounts and answers, never a card's words; an invariant keeps decision statuses inside `decisions.js`) and only counts tickets (the one exception in the tickets-table invariant). **One source for both screens:** the window's `BriefPanel.jsx` draws `sections[].lines` through the `brief.get` command, and Telegram's `/brief` and the morning digest send `renderBriefText(brief)`, built from those same lines, so they cannot disagree. `telegram/digest.js` sends the digest once a day at `DIGEST_TIME_IST` (default 09:00 IST; `off` disables it; a bad value disables it and the app says so with a `digest.problem` event). If the app was closed at that time it sends on start, but only within six hours after; the day's send is written to the audit log so a restart never sends it twice, the attempt is audited before it is sent, and a failure is retried after five minutes, at most six times a day. The "Waiting for you" section lists up to five waiting cards, oldest first, with each card's one-sentence question, its kind and how long it has waited (`decisions.summary` passes on only those). Telegram's `/status [team]` sends `renderStatusText` from `teams/overview.js`, built from the same overview as the Teams page (an eval keeps the status words identical). Graded by the `daily-brief` and `morning-digest` evals.

### Database

Supabase Postgres, defined in `supabase/migrations/*.sql` (applied in filename order; add new migrations, never edit applied ones) with a dev-only `supabase/seed.sql`. The runtime is the only database client and uses the service key (bypasses row-level security); the renderer never touches the database. The row-level-security policies are keyed on a `pod_id` JWT claim for future pod-scoped clients, and the integrity rules (append-only `audit_log`, frozen `decisions`) are triggers, so they hold for everyone. Every new public table must enable row-level security (the `database-schema` eval fails otherwise) and must be added to that suite's fixture. `npm run eval database-schema` tests the migrations on an in-process Postgres (PGlite) with no credentials; `npm run check:db` checks that the tables exist in the real project (read-only).

### Security constraints to preserve

The window is configured with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`, and `index.html` sets a strict CSP (`default-src 'self'; script-src 'self'; style-src 'self'`). Consequences when adding features:

- Renderer code cannot `require` anything or touch Node/Electron APIs directly; expose each capability explicitly from `preload.js` via `contextBridge` (ideally backed by `ipcMain.handle` / `ipcRenderer.invoke`, not by exposing raw `ipcRenderer`).
- Because the preload is sandboxed, it can only `require` `electron` (limited subset) and a few built-ins — not arbitrary local modules or npm packages.
- No inline `<script>`/`<style>`, inline `style=` attributes or remote resources; the production CSP blocks them. Put code and CSS in separate files under `src/renderer/` (Vite bundles them).
- The strict CSP lives in `src/renderer/index.html` and applies to builds. `npm run dev` needs inline scripts (React Refresh) and a websocket (HMR), so `electron.vite.config.mjs` has a plugin (`dev-only-csp`, `apply: 'serve'`) that relaxes the CSP in dev only. Keep it `serve`-only: a dev-only success can hide a CSP violation that breaks the production build, so check features with `npm start` too. The `invariants` suite guards this.
